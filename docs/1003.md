## 3. P0-4 마무리와 오류 처리 2건

### 3-1. 생성 로그에 content hash·입력 글자 수 (`dec6a78`)

- `quiz.generation` 로그에 `contentHash`(추출 텍스트의 SHA-256)와 `textChars`를 추가했다.
- 200,000자 초과 거절도 `quiz.generation status=REJECTED_TOO_LONG textChars=… studId=…`로 남긴다. P1-1 청킹이 필요한지 판단할 빈도 측정용이다.
- 09-29에 넣었던 `QuizGenerationInput.contentHash()`는 이후 정리 작업에서 빠져 있었다. 이번에는 텍스트만 해시한다.

### 3-2. 없는 경로·허용되지 않은 메서드가 500으로 응답되던 문제 (`39ec9c5`)

- `GlobalExceptionHandler`의 `Exception` 핸들러가 `NoResourceFoundException`(404)과 `HttpRequestMethodNotSupportedException`(405)까지 잡아 500으로 바꾸고 있었다.
- `handleUnexpected`에서 예외가 `org.springframework.web.ErrorResponse`이면 그 상태 코드로 응답하게 했다. errorCode는 `NOT_FOUND`, `METHOD_NOT_ALLOWED`다.
- 계획은 별도 핸들러였지만, `@ExceptionHandler`가 인터페이스 타입을 받지 않아 컴파일에 실패했다. 그래서 기존 핸들러 안의 분기로 바꿨다.

### 3-3. 풀이 저장 실패가 제출 완료로 보이던 문제 (`bdc16cb`)

- `CBTPlayer.handleSubmit`은 저장에 실패해도 결과 화면으로 넘어갔다.
- 이제 결과 화면으로 넘기지 않고 서버 `message`(없으면 "풀이 결과를 저장하지 못했습니다. 다시 시도해 주세요.")를 alert로 보여준다. 답안이 남아 있어 다시 제출할 수 있다.

## 4. AI 문제 생성 학생별 호출 제한 (`be8aaf9`, P1-2)

- 상한: 동시 생성은 학생당 1건, 호출은 학생당 10분에 5회. 동시 생성 제한으로 idempotency key를 대신한다.
- `QuizService`가 메모리에 진행 중 학생 집합과 학생별 최근 호출 시각을 둔다.
  - 입력 검증을 모두 통과한 뒤 AI 호출 직전에 검사한다. 입력 오류는 횟수에 넣지 않고, AI 호출 실패는 넣는다.
  - 진행 중 상태는 `finally`에서 항상 해제한다.
- 초과하면 새 `TooManyRequestsException`으로 429 `TOO_MANY_REQUESTS`를 반환하고, `quiz.generation status=RATE_LIMITED reason=CONCURRENT|WINDOW` 로그를 남긴다.
- 서버 1대 메모리 기준이며 재시작하면 초기화된다(`ponytail:` 주석).
- 생성 시작 시각은 호출 제한 검사 시각을 재사용했다. `clock` 호출 순서에 의존하는 기존 30초 예산 테스트를 유지하기 위해서다.

## 5. 이력 대비 중복 문제 재생성 (`3bcb74b`, P1-4)

- 같은 학생·같은 강의의 최근 문제 200개(`QuestionRepository.findRecentQuestionTexts`)와 문제 문장을 비교한다. 정규화(trim·소문자) 후 정확 일치만 본다.
  - 정규화는 `QuizQualityValidator.normalize`를 재사용한다.
- 검증을 통과한 결과에 중복이 있으면 1회 재생성한다.
  - 재생성 후에도 중복이 남으면 실패시키지 않고 저장한다. 두 결과 중 중복이 적은 쪽을 쓴다.
  - 재생성이 검증 실패·AI 오류로 끝나면 앞선 결과를 저장한다.
  - 30초 예산을 넘었으면 재생성하지 않는다.
- `quiz.generation` 로그에 `historyDuplicates`를 추가했다.
- 프롬프트는 바꾸지 않았다. AI가 이전 문제를 모르므로 재생성은 중복을 확률적으로만 줄인다. 이전 문제 목록을 프롬프트에 넣는 방식은 승인이 필요해 후속 과제로 남겼다.

## 8. 주관식 채점 정규화 (`eaf58e9`, P2-6 1차)

- 주관식(`SHORT_ANSWER`)만 소문자 → 모든 공백 제거 → 앞뒤 문장부호(`. , ! ? ; : 따옴표 。`) 제거 후 비교한다. "운영 체제." = "운영체제". "C++"의 `+`나 괄호는 지우지 않는다.
- 객관식·OX는 기존 trim + 소문자를 유지한다. 넓히면 서로 다른 보기가 같아질 수 있다.
- 서버 `QuizService.isAnswerCorrect(type, …)`와 프론트 `CBTPlayer.isCorrectAt`에 같은 규칙을 넣고, 함께 바꿔야 한다는 주석을 양쪽에 남겼다. 서버 정규식은 JS `\s`와 맞추려고 `(?U)`로 유니코드 공백까지 지운다.
- 이미 저장된 풀이 기록(`UserAnswer.isCorrect`)은 다시 채점하지 않는다.

## 10. 수동 테스트와 후속 수정 (`4e20a3a`, `a49ec5d`)

`local` 프로필 백엔드와 테스트 계정(`202612345`)으로 실제 API와 Gemini를 호출했다. 테스트 노트·퀴즈·풀이 기록은 모두 지웠고 서버도 종료했다.

- 난이도: 같은 노트(문단 5개)로 EASY는 용어 회상(정답 "FIFO", "스래싱"), HARD는 사례 추론("프레임을 늘렸는데 페이지 폴트가 늘었다…") 문제가 나왔다.
- 채점: "스 래 싱."과 "스래싱", "O P T 알 고 리 즘."과 "OPT 알고리즘"이 정답으로 채점됐다(4/4). 틀린 답 대조군은 0점이었다.
- 404: `/api/nope` → 404 `NOT_FOUND`.
- 로그: `promptVersion`, `historyDuplicates=0`, `contentHash`, `textChars=515`가 정상 기록됐다.

발견해 고친 문제 2건:

- **HARD 주관식 정답이 서술형 (`4e20a3a`):** HARD 주관식 정답이 2~3문장으로 나와 정확 일치 채점으로는 맞힐 수 없었다. 프롬프트 준수 사항 5번 "주관식 정답은 하나의 단어나 짧은 구(20자 이내)"를 추가하고 `PROMPT_VERSION`을 `2026-10-03.2`로 올렸다. 재생성 결과 정답이 "LRU", "미래 참조 예측 불가능", "워킹 셋 모델"로 짧아졌고 문제는 여전히 사례 추론형이었다.
- **255자 초과 답안이 409 (`a49ec5d`):** `user_answers.submitted_answer`(VARCHAR 255)를 넘으면 DB 오류로 409 "다른 데이터와 연결되어 있어…"가 났다(기존 문제). `QuizAttemptRequest.UserAnswerRequest.submittedAnswer`에 `@Size(max = 255)`를 두어 400 `VALIDATION_FAILED` "답안은 255자 이하로 입력해 주세요."로 바꾸고, `CBTPlayer` 주관식 입력에 `maxLength={255}`를 줬다. 실서버에서 256자 제출 → 400을 확인했다.
