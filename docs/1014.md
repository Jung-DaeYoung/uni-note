## 2. 마이페이지 계획 검토와 보완

`docs/current-plan.md`(마이페이지 구현 계획)를 실제 코드와 대조했다. 방향과 범위는 적절했고, 활동 원천 엔티티에 모두 학생 FK와 날짜 필드가 있어 DB 변경 없이 구현할 수 있었다. 아래 12개 항목을 계획에 반영했다.

사실과 달랐던 부분:

1. 복습 활동은 따로 기록되지 않는다. 복습 재풀이도 `POST /api/quiz/attempts`로 저장되는 `QuizAttempt`이고, `UserAnswer`에는 날짜가 없다. → 활동을 "퀴즈 풀이(복습 포함)"와 "오답노트 담기(`IncorrectNoteItem.addedAt`)"로 다시 정의했다.
2. `Note.updatedAt`은 `@UpdateTimestamp`라 제목 변경·트리 이동에도 바뀌고, 생성 직후에는 `createdAt`과 같다. → 노트 중복 집계 규칙을 정했다.
3. 직접 만든 강의에는 Enrollment가 없다. → 강의 목록은 `DashboardService`와 같은 원천을 쓴다.

빠져 있던 부분:

4. API 계약(`GET /api/mypage`와 응답 예시)
5. 학기 경계 날짜(3/1~6/30, 9/1~12/31, 방학에는 직전 학기)
6. 시간대: 서울 기준 날짜, 주입한 `Clock`
7. 백엔드 테스트가 Mock뿐이라 JPQL 오류는 기동 시점에만 드러난다 → 검증에 bootRun 추가
8. 히트맵 색 단계, 최근 활동 20건, 통계 카드는 전체 누적
9. 링크 대상(공유 시험은 상세 라우트가 없어 목록으로 이동)
10. 익명 게시판의 내 글은 본인 응답에만 담는다
11. API 문서 경로는 `docs/api.md`
12. 범위가 커서 두 커밋으로 나눈다(1차: 프로필·통계·히트맵, 2차: 강의별 현황·최근 활동·내 콘텐츠)

## 3. 마이페이지 1차 구현 (`2051d2f`)

### 백엔드

- `GET /api/mypage` (`MyPageController` → `MyPageService`)
  - 인증된 학번(`authentication.getName()`)의 데이터만 조회한다.
  - 응답 `MyPageResponse`(record): `profile`, `semester`, `summary`, `heatmap`
- `MyPageActivityRepository`
  - 여러 엔티티에 걸친 "학생 한 명의 활동" 쿼리 20개를 한 파일에 모았다. `Repository<Student, Long>`를 상속하고 `@Query`만 둔다.
  - 히트맵용 쿼리는 엔티티를 불러오지 않고 날짜 컬럼만 조회한다. 서비스가 날짜별로 합친다. DB별 날짜 함수에 의존하지 않는다.
- 학기 계산 `MyPageService.semesterOf`
  - 1학기 3/1~6/30, 2학기 9/1~12/31. 7~8월은 그해 1학기, 1~2월은 전년도 2학기.
  - 오늘 날짜는 기존 `Clock` 빈에 `Asia/Seoul`을 적용해 구한다.
- 노트 집계: 생성일에 1회, 마지막 수정일이 생성일과 다른 날이면 그날 1회를 더한다.
- 통계: 전체 누적. `commentCount`는 강의 게시판·공유 노트·공유 시험 댓글의 합, `sharedCount`는 공유 노트·공유 시험의 합.

### 프론트엔드

- `/mypage` 보호 라우트, 사이드바 "오답노트" 아래 "마이페이지" 메뉴
- `pages/MyPage.jsx`: 프로필, 학기 활동 히트맵, 통계 카드 7개, 로딩·오류·빈 상태
- `components/mypage/ActivityHeatmap.jsx`
  - 학기 시작 주의 일요일부터 종료일까지 주 단위 열로 채운다. 빈 날짜는 프론트가 채운다.
  - 색 단계 0 / 1–2 / 3–5 / 6–9 / 10 이상, 라이트·다크 모드
  - 날짜와 횟수는 `title` 툴팁으로 보여준다. 칸이 약 120개라 키보드 포커스는 넣지 않았다.

### 계획과 다르게 한 부분

- 쿼리를 엔티티별 Repository 10곳에 나누지 않고 한 파일에 모았다. 서비스 의존성과 테스트 mock이 하나로 줄어든다.
- SQL `GROUP BY` 대신 날짜 컬럼만 조회해 Java에서 합산했다.
- 2차 필드(`courseProgress`, `recentActivities`, `myContents`)는 응답에서 비워 두지 않고 아예 넣지 않았다. 2차 구현 때 추가한다.

### 테스트

- `MyPageServiceTest`
  - 학기 경계 8개(2/28, 1/1, 3/1, 6/30, 7/1, 8/31, 9/1, 12/31)
  - 시스템 시간대가 UTC여도 서울 날짜로 학기를 정하는지
  - 본인 데이터·학기 기간 조건, 원천별 날짜 합산, 노트 중복 집계, 빈 데이터 응답, 댓글·공유 합산
- `ActivityHeatmap.test.jsx`: 색 단계 구간, 학기 범위 채우기(122일), 셀 표시
- 결과: `gradlew test` 통과, 프론트 lint·vitest(80개)·build 통과
- 서버 재기동 성공으로 JPQL 20개 유효성 확인. 인증 없이 호출하면 403(기존 대시보드 API와 같음).

### 남은 확인

- 실제 계정으로 로그인한 상태의 `/mypage` 화면과 API 응답은 수동 테스트가 필요하다. 문서의 예시 계정(20211234 / 1234)으로는 로그인되지 않았다.
- 날짜 저장값은 서버 JVM 시간대를 따른다. 운영 서버가 UTC면 히트맵 날짜가 최대 9시간 밀릴 수 있다. 기존 모든 시각 표시에도 해당하는 문제라 이번 범위에서는 손대지 않았다.
