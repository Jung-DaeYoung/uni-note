## 주의사항 및 잠재적 문제

### 1. Java에서 PEM 인증서를 쓰는 방법

- Java 21의 기본 KeyStore 형식은 JKS와 PKCS12 같은 것들이고 PEM은 없다. Connector/J 9.1.0은 `trustCertificateKeyStoreType`으로 JVM이 지원하는 형식만 받는다. 그래서 `global-bundle.pem`을 그대로 지정할 수 없고 **PKCS12로 바꿔야 한다.** 공개된 사양 기준이며, 실제로는 기동 로그로 확인한다.
- `keytool -importcert`는 여러 인증서가 이어진 PEM 파일에서 **첫 번째 인증서만** 가져온다. 그래서 인증서별로 나눈 뒤 하나씩 넣는다.

  ```bash
  sudo mkdir -p /home/ubuntu/rds-certs && cd /home/ubuntu/rds-certs
  sudo cp <global-bundle.pem 위치> ./rds-bundle.pem
  sudo awk '/BEGIN CERT/{n++} {print > ("rds-ca-" n ".pem")}' rds-bundle.pem
  read -rs TSPW; export TSPW
  for f in rds-ca-*.pem; do
    sudo -E docker run --rm -e TSPW -v /home/ubuntu/rds-certs:/certs eclipse-temurin:21-jre \
      keytool -importcert -noprompt -alias "${f%.pem}" -file "/certs/$f" \
      -keystore /certs/rds-truststore.p12 -storetype PKCS12 -storepass:env TSPW
  done
  grep -c 'BEGIN CERT' rds-bundle.pem   # 이 숫자와
  sudo -E docker run --rm -e TSPW -v /home/ubuntu/rds-certs:/certs eclipse-temurin:21-jre \
    keytool -list -keystore /certs/rds-truststore.p12 -storepass:env TSPW | grep -c trustedCertEntry  # 이 숫자가 같아야 함
  ```

  `-storepass:env`를 쓰면 비밀번호가 명령 인자나 shell history에 남지 않는다.

- JDBC url은 다음과 같다. `useSSL`과 `requireSSL`은 지운다.

  ```
  jdbc:mysql://${DB_HOST}:${DB_PORT:3306}/${DB_NAME:uninote_db}?serverTimezone=Asia/Seoul&sslMode=VERIFY_IDENTITY&trustCertificateKeyStoreUrl=file:/run/secrets/rds-truststore.p12&trustCertificateKeyStoreType=PKCS12&trustCertificateKeyStorePassword=${TRUSTSTORE_PASSWORD}&allowPublicKeyRetrieval=false
  ```

- **이 url을 어디에 넣을지 정해야 한다.**
  - (A) `application-prod.yaml` 수정: 설정이 한 곳에 모이므로 권장한다. 다만 main에 병합하고 이미지를 다시 빌드해야 하고, main에 push할 때마다 Netlify 빌드 크레딧 15가 소모된다.
  - (B) `backend.env`에 `SPRING_DATASOURCE_URL=<위 url>` 추가: 코드를 바꾸지 않아도 yaml보다 우선 적용된다. 대신 설정이 두 곳으로 나뉜다.
- JVM 전체 옵션(`-Djavax.net.ssl.trustStore`)으로 걸면 안 된다. 기본 신뢰 저장소를 대체해서 Gemini HTTPS 호출이 깨진다. [추론]
- `DB_HOST`에는 RDS 엔드포인트 호스트명을 넣어야 한다. IP나 CNAME이면 호스트명 검증에서 실패한다.
- 검증 방법: 앱이 정상 기동하는지 확인한 뒤, **일부러 `DB_HOST`를 RDS의 IP로 바꿔서 기동이 실패하는지** 확인한다. 실패해야 검증이 실제로 동작하는 것이다.

### 2. 시간대

`notes.created_at`은 TIMESTAMP 타입이라, RDS 시간대가 UTC면 기존 노트 시각이 9시간 어긋난다. `SELECT @@global.time_zone;`으로 확인하고, UTC라면 커스텀 파라미터 그룹에서 `Asia/Seoul`로 바꾼다. 반영하려면 RDS 재부팅이 필요할 수 있다. [추측]

### 3. 데이터 이전과 validate의 순서

운영 설정은 `ddl-auto: validate`라서 RDS에 스키마가 없으면 기동이 실패한다. **컨테이너를 실행하기 전에 덤프 이전을 먼저 해야 한다.**

### 4. backend.env 관련

- `FILE_SIGNING_SECRET`은 줄 자체가 없으면 괜찮지만, `FILE_SIGNING_SECRET=`처럼 빈 값으로 두면 업로드할 때 500 오류가 난다(`docs/current_problem.md` 분석 참고).
- 앞으로 `TRUSTSTORE_PASSWORD`를 추가해야 한다.
- Compose의 `env_file`은 `docker run --env-file`과 달리 값 안의 `$`를 변수로 치환한다 [추측: Compose v2 동작]. 비밀번호에 `$`가 들어 있다면 바꾸거나 `$$`로 이스케이프한다.

### 5. 포트 노출

Docker가 여는 포트는 UFW 방화벽을 거치지 않는다. 반드시 `127.0.0.1:8080:8080`으로 바인딩한다. Security Group에서도 8080은 열지 않는다.

### 6. 메모리 (t3.small, 2GB)

JVM은 기본적으로 메모리의 25%(약 500MB)만 힙으로 쓴다. 이 정도로 충분할 가능성이 높지만, AI 퀴즈 생성 때 PDF를 메모리에 올리므로 swap 2GB를 만들어 두는 것을 권장한다. [추측]

### 7. 이미지 태그와 로그

- `latest` 태그만 쓰면 이전 버전으로 되돌릴 수 없다. `docs/배포환경 설계.md`대로 git SHA 태그를 함께 붙인다.
- Docker 로그는 기본적으로 크기 제한 없이 쌓이므로 로테이션을 설정한다.

### 8. Netlify 연동 순서

Netlify는 HTTPS라서 HTTP 백엔드를 호출하면 브라우저가 mixed content로 차단한다. **HTTPS를 적용한 뒤에야** 연동 테스트가 가능하다. `CORS_ALLOWED_ORIGINS`에는 실제 Netlify origin을 넣고 끝에 `/`를 붙이지 않는다.

### 9. Nginx 설정

`client_max_body_size 11m`과 `proxy_read_timeout 120s`를 빠뜨리면 업로드가 413, 퀴즈 생성이 504로 실패한다. 둘 다 `docs/배포환경 설계.md` 7장에 있다.

참고: 로컬 PC의 `main` 브랜치는 origin보다 23커밋 뒤처져 있다. EC2와는 관계없다.

## 다음 진행 순서 (의존성 순)

1. **RDS 점검**: `time_zone`, `require_secure_transport`, `uninote_db`의 문자셋 확인. 필요하면 파라미터 그룹을 수정하고 재부팅한다. 앱 전용 계정도 만든다.
2. **데이터 이전**: 로컬 백엔드를 중지하고 mysqldump로 덤프한 뒤, 업로드 참조가 0건인지 다시 확인한다. scp로 옮기고 `mysql --ssl-mode=VERIFY_IDENTITY --ssl-ca=...`로 가져온 다음, 테이블별 `COUNT(*)`와 `notes.created_at`을 로컬과 비교한다. 끝나면 덤프 파일을 삭제한다.
3. **truststore 만들기**: 위 1번 스크립트를 실행하고, `backend.env`에 `TRUSTSTORE_PASSWORD`를 추가한다.
4. **JDBC url 적용**: A(yaml)와 B(env) 중 하나를 정한다. A라면 수정 → 병합 → EC2에서 pull → SHA 태그로 다시 빌드한다.
5. **`/opt/uninote/uploads` 확인**: `sudo mkdir -p /opt/uninote/uploads`
6. **docker-compose.yml 작성** (예시는 `/opt/uninote/` 아래에 두는 기준):

   ```yaml
   services:
     backend:
       image: uninote-backend:${TAG:-latest}
       container_name: uninote-backend
       restart: unless-stopped
       env_file: /home/ubuntu/uni-note/backend.env
       ports: ["127.0.0.1:8080:8080"]
       volumes:
         - /opt/uninote/uploads:/app/uploads
         - /home/ubuntu/rds-certs/rds-truststore.p12:/run/secrets/rds-truststore.p12:ro
       logging:
         driver: json-file
         options: { max-size: "10m", max-file: "5" }
   ```

7. **실행과 검증**: `docker compose up -d` 후 `docker compose logs -f`로 validate 통과와 Hikari 연결을 확인한다. 이어서 일부러 IP로 접속해 실패하는지 보는 음성 테스트를 하고, `curl 127.0.0.1:8080`으로 응답을 확인한다.
8. **업로드 볼륨 확인**: 컨테이너를 재시작한 뒤에도 업로드한 파일이 남아 있는지 확인한다. 이 테스트는 HTTPS 적용 후에 해도 된다.
9. **Nginx**: 80 포트로 구성하고 위 두 설정을 넣는다. Security Group에서 80과 443을 연다.
10. **DuckDNS와 Certbot**: DuckDNS가 Elastic IP를 가리키는지 확인한 뒤 HTTPS를 적용한다.
11. **Netlify**: `VITE_API_BASE_URL=https://uninote.duckdns.org`으로 설정하고 재배포한다. 그다음 로그인, 노트 자동 저장, 업로드, AI 퀴즈 생성, 커뮤니티 기능을 차례로 테스트한다.
12. **마무리**: RDS 삭제 방지와 백업 보존 기간을 확인하고, `docs/배포환경 설계.md`의 SSL 부분(REQUIRED → VERIFY_IDENTITY)을 갱신한다.
