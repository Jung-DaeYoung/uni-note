# UniNote 배포환경 설계

## 1. 목표

UniNote를 다음 구조로 배포한다.

- Frontend: Netlify
- Backend: AWS EC2의 Docker 컨테이너
- Database: AWS RDS MySQL
- HTTPS reverse proxy: EC2 Nginx
- 파일 저장: 초기에는 EC2 영속 볼륨, 이후 S3 이전 검토

```text
사용자 브라우저
  ├─ HTTPS: 정적 파일 → Netlify (React 빌드 결과)
  └─ HTTPS: API 요청 → EC2 Nginx :443
                         ↓ 127.0.0.1:8080
                       Docker: Spring Boot Backend ── /app/uploads → EC2 /opt/uninote/uploads
                         ↓ private network (TLS)
                       AWS RDS MySQL
```

API 요청은 Netlify를 거치지 않고 브라우저에서 EC2로 직접 전달된다. JWT는 쿠키가 아니라 `Authorization` 헤더로 전송하므로 Frontend와 API의 도메인이 달라도 쿠키 설정은 필요 없다.

## 2. 현재 프로젝트 기준 확인사항

- Backend는 Java 21, Spring Boot 3.4.2를 사용한다.
- 운영 설정은 `SPRING_PROFILES_ACTIVE=prod` 프로파일을 사용한다.
- 운영 JPA 설정은 `ddl-auto: validate`이므로 애플리케이션이 DB 스키마를 자동 생성하거나 변경하지 않는다.
- 저장소에는 스키마 SQL과 마이그레이션 도구가 없다.
- 업로드 파일은 실행 디렉터리 기준 `uploads`에 저장되며, 파일 크기 제한은 10MB다.
- AI 퀴즈 생성 요청은 최악의 경우 약 90초가 걸린다.
- 시간은 JVM 기본 시간대를 따른다. `ClockConfig`, `LocalDateTime.now()`, `@CreatedDate`가 해당한다.
- Actuator가 없어 별도의 헬스 체크 경로가 없다.
- Gemini 연동 키는 `GEMINI_API_KEY` 환경변수로 주입하며, 값이 없으면 기동에 실패한다.
- Frontend API 주소는 빌드 시 `VITE_API_BASE_URL`로 지정한다.
- `VITE_API_BASE_URL`은 Vite CSP 설정에도 반영되므로 값을 바꾸면 Netlify 재배포가 필요하다.
- SPA 라우팅용 `frontend/public/_redirects`는 이미 존재한다.

## 3. Backend 운영 환경변수

EC2의 `/opt/uninote/backend.env`에 저장하고 Docker 컨테이너로 주입한다. 이 파일은 Git에 커밋하지 않는다.

```env
SPRING_PROFILES_ACTIVE=prod
TZ=Asia/Seoul

DB_HOST=<RDS endpoint>
DB_PORT=3306
DB_NAME=uninote_db
DB_USERNAME=<db user>
DB_PASSWORD=<db password>

JWT_SECRET=<32바이트 이상 랜덤 값>
JWT_EXPIRATION=86400000

FILE_SIGNING_SECRET=<파일 서명 키>
CORS_ALLOWED_ORIGINS=https://<netlify-site>.netlify.app

GEMINI_API_KEY=<gemini api key>
```

주의사항:

- `TZ=Asia/Seoul`을 빠뜨리면 컨테이너가 UTC로 동작해 새로 저장되는 시간이 9시간 어긋난다.
- `CORS_ALLOWED_ORIGINS`에는 실제 Frontend origin만 입력한다. 정확히 일치하는 origin만 허용되므로 커스텀 도메인을 쓰면 콤마로 함께 넣고, Netlify 미리보기 주소는 허용되지 않는다는 점을 감안한다.
- origin 끝에 `/`를 붙이지 않는다.
- 운영값에 `localhost`, `127.0.0.1`, `*`를 사용하지 않는다.
- env 파일의 값은 따옴표로 감싸지 않는다. `docker --env-file`은 따옴표를 값의 일부로 읽는다.
- JWT, 파일 서명 키, DB 비밀번호, Gemini 키를 소스 코드나 Dockerfile에 넣지 않는다.

`FILE_SIGNING_SECRET` 값 결정:

- 서명된 파일 URL이 노트 본문에 저장되므로, 키가 바뀌면 기존 이미지와 PDF가 403이 된다.
- 로컬 데이터를 유지하므로 로컬 `application-local.yaml`의 `file.signing-secret` 값을 그대로 넣는다. 현재 `jwt.secret` 값과 다르므로 혼동하지 않는다.
- 한 번 정한 값은 이후 변경하지 않는다.

## 4. Docker 구성

Backend에 다음 파일을 추가한다. 컨테이너가 하나이므로 Compose는 사용하지 않고 `docker run`으로 실행한다.

```text
backend/
├─ Dockerfile
└─ .dockerignore
```

`backend/Dockerfile`:

```dockerfile
FROM eclipse-temurin:21-jdk AS build
WORKDIR /workspace

COPY gradlew gradlew.bat build.gradle settings.gradle ./
COPY gradle gradle
# gradlew가 Git에 실행 권한 없이(100644) 등록되어 있다.
RUN chmod +x gradlew
RUN ./gradlew dependencies --no-daemon

COPY src src
RUN ./gradlew bootJar --no-daemon

FROM eclipse-temurin:21-jre
WORKDIR /app

RUN mkdir -p /app/uploads
COPY --from=build /workspace/build/libs/*.jar app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

`backend/.dockerignore`:

```text
build/
.gradle/
uploads/
*.log
src/main/resources/application-local.yaml
```

`application-local.yaml`에는 실제 비밀값이 들어 있다. 제외하지 않으면 작업 폴더에서 빌드할 때 `COPY src src`로 이미지에 포함된다.

컨테이너 실행 예시:

```bash
docker run -d \
  --name uninote-backend \
  --restart unless-stopped \
  -p 127.0.0.1:8080:8080 \
  --env-file /opt/uninote/backend.env \
  -v /opt/uninote/uploads:/app/uploads \
  uninote-backend:<git-sha>
```

`127.0.0.1:8080`으로만 바인딩하여 Backend를 외부에 직접 노출하지 않고 Nginx를 통해 접근하게 한다.

## 5. AWS EC2

권장 환경:

- Ubuntu 24.04 LTS
- Docker Engine
- 최소 2GB RAM 이상, 2GB 인스턴스에서 이미지를 빌드하면 swap 2GB 추가
- 업로드 파일을 고려한 충분한 EBS 용량
- Elastic IP 할당 (없으면 인스턴스를 중지했다 시작할 때 IP가 바뀌어 DNS가 끊긴다)

Security Group:

| 포트 | 허용 대상 | 용도 |
|---|---|---|
| 22 | 관리자 IP만 | SSH |
| 80 | 전체 | HTTP 및 인증서 발급 |
| 443 | 전체 | HTTPS |
| 8080 | 열지 않음 | Backend 내부 접근 |

EC2에서 RDS로 연결하기 위한 RDS Security Group의 3306 포트는 EC2 Security Group만 허용한다.

## 6. AWS RDS MySQL

운영 프로파일은 다음과 같이 스키마 자동 변경을 막는다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

- 퍼블릭 액세스를 끄고, 자동 백업을 켠다.
- DB는 `utf8mb4`로 명시해 생성한다.
- 엔진은 MySQL 8.4를 선택한다. RDS의 MySQL 8.0은 2026-07-31에 표준 지원이 끝나 Extended Support 요금 대상이다. 로컬(8.0.45)과 메이저 버전이 다르므로 이전 후 12장 6단계 점검을 빠짐없이 수행한다.

로컬 데이터를 유지하기로 결정했으므로, `mysqldump`로 스키마와 데이터를 함께 이전한다 (12장 3단계).

로컬 DB는 `ddl-auto: update`로 만들어져 지금은 쓰지 않는 컬럼이 남아 있을 수 있다. `validate`는 남은 컬럼을 검사하지 않으므로, 기동 성공만으로 끝내지 말고 쓰기 동작까지 확인한다.

상시 운영에서 `ddl-auto: update`를 사용하지 않는다. 배포 후 엔티티를 변경할 때는 변경 SQL을 RDS에 먼저 적용하고 새 이미지를 배포한다. 스키마 변경이 잦아지면 Flyway 도입을 검토한다.

## 7. Nginx 및 HTTPS

권장 요청 흐름:

```text
https://uninote.duckdns.org
        ↓
Nginx :443
        ↓
127.0.0.1:8080
        ↓
Spring Boot Docker
```

초기 Nginx 설정 예시:

```nginx
server {
    listen 80;
    server_name uninote.duckdns.org;

    # 앱 제한 10MB + multipart 여유분. 기본값 1MB면 1MB 초과 업로드가 413이 된다.
    client_max_body_size 11m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        # AI 퀴즈 생성은 최대 약 90초. 기본값 60초면 504가 된다.
        proxy_read_timeout 120s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Nginx가 직접 반환한 413·504 응답에는 CORS 헤더가 없어, 브라우저에서는 네트워크 오류로 보인다. 이 증상이 보이면 Nginx 로그를 먼저 확인한다.

DNS를 연결한 뒤 Certbot으로 HTTPS를 적용하고, Frontend는 `https://uninote.duckdns.org`을 Backend 주소로 사용한다.

## 8. Netlify 설정

Netlify 환경변수 (`/api`를 붙이지 않고 origin만 입력한다):

```env
VITE_API_BASE_URL=https://uninote.duckdns.org
```

Build 설정 (Netlify 웹 UI 입력 기준):

```text
Base directory: frontend
Build command: npm run build
Publish directory: frontend/dist
```

UI가 Base directory를 자동으로 앞에 붙이는 경우가 있으므로, 저장 후 최종 경로가 `frontend/frontend/dist`가 아닌 `frontend/dist`인지 확인한다.

Netlify Free 플랜은 월 300크레딧이고 프로덕션 배포 1회에 15크레딧을 쓴다. 크레딧이 소진되면 사이트가 다음 주기까지 중지되므로, Production branch는 `main`으로 두고 배포할 변경만 병합한다.

React Router의 직접 접근은 기존 `frontend/public/_redirects`로 지원한다.

환경변수는 빌드 시 반영되므로 값을 변경한 뒤 반드시 Netlify 재배포를 수행한다.

## 9. 업로드 파일 저장

### 초기 방식: EC2 영속 볼륨

```text
EC2 host: /opt/uninote/uploads
Docker:   /app/uploads
```

필수 조건:

- bind mount 사용
- 업로드 디렉터리 정기 백업 (EBS 스냅샷 자동화)
- EC2 교체 및 장애 시 복구 절차 마련
- 초기 이전 시 DB와 `backend/uploads`를 함께 옮긴다

### 장기 방식: S3

장기적으로는 다음 구조로 이전한다.

```text
S3 bucket
  ├─ 업로드 파일 저장
  ├─ EC2 IAM Role로 접근
  └─ DB에는 object key 또는 서명 URL 정보 저장
```

S3 이전 시 `ImageUploadController`와 `QuizAiGenerationService`의 로컬 파일 접근 로직도 함께 변경한다.

## 11. 운영 점검 항목

- Netlify에서 Backend HTTPS 요청이 성공하는가
- 로그인 및 JWT 인증이 정상 동작하는가
- 401/403 응답 처리가 정상인가
- CORS 오류가 없는가
- 1MB가 넘고 10MB 이하인 파일이 업로드되는가
- 파일 업로드 후 새로고침과 컨테이너 재시작 뒤에도 파일이 유지되는가
- 이전한 기존 노트의 이미지와 PDF가 보이는가
- 퀴즈 생성이 504 없이 완료되고 Gemini API 호출이 성공하는가
- 새로 저장한 데이터의 시간이 한국 시간과 일치하는가
- 노트 작성, 게시글 작성, 퀴즈 풀이 등 쓰기 동작이 DB 오류 없이 저장되는가
- RDS 재시작 후 데이터가 유지되는가
- Docker 컨테이너 자동 재시작이 동작하는가
- Backend API가 HTTPS를 통해서만 노출되는가 (`http://<EC2 IP>:8080` 접속 불가)
- DB, JWT, 파일 서명, Gemini 키가 Git과 Docker 이미지에 포함되지 않았는가

## 12. 실행 가이드라인

명령의 `<...>`는 실제 값으로 바꾼다. 각 단계의 **완료 기준**을 통과한 뒤 다음 단계로 넘어간다.

### 0단계: 사전 결정

- [x] 로컬 데이터 유지
- [x] API 도메인: DuckDNS 무료 서브도메인 `uninote.duckdns.org` 사용. HTTPS 인증서 발급에 필요하다. https://www.duckdns.org 에서 미리 만들어 둔다
- [ ] Netlify 사이트 주소 확보. 사이트를 먼저 만들어 `CORS_ALLOWED_ORIGINS`에 넣을 origin을 정한다

### 1단계: 저장소 준비

4장 내용대로 `backend/Dockerfile`, `backend/.dockerignore`를 추가하고 커밋한다. 이미지는 EC2에서 빌드하므로 로컬 PC에는 Docker가 필요 없고, 첫 빌드 검증은 3단계에서 이루어진다.

**완료 기준:** `git diff`에 비밀값이 없고, EC2에서 받을 수 있도록 원격 저장소에 반영됨. 비공개 저장소면 EC2에 읽기 전용 deploy key를 등록한다.

### 2단계: AWS 리소스 생성

1. EC2 Security Group과 RDS Security Group을 5장 표대로 만든다.
2. EC2(Ubuntu 24.04)를 만들고 Elastic IP를 연결한다.
3. RDS MySQL을 같은 VPC에 만든다. 퍼블릭 액세스는 끄고 자동 백업을 켠다.
4. EC2에 필요한 도구를 설치한다.

```bash
sudo apt update
sudo apt install -y docker.io nginx certbot python3-certbot-nginx mysql-client git
sudo usermod -aG docker ubuntu   # 재접속 후 적용

# 2GB 인스턴스에서 이미지를 빌드할 때만
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

sudo mkdir -p /opt/uninote/uploads
```

5. RDS에 DB를 만든다.

```bash
mysql --ssl-mode=REQUIRED -h <RDS endpoint> -u <admin> -p \
  -e "CREATE DATABASE uninote_db CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
```

**완료 기준:** EC2에서 RDS에 접속되고, 외부에서는 RDS와 8080에 접속되지 않음.

### 3단계: 환경변수 파일과 이미지 준비

```bash
sudo nano /opt/uninote/backend.env   # 3장 내용 입력
sudo chmod 600 /opt/uninote/backend.env
openssl rand -base64 48              # JWT_SECRET 등 랜덤 값 생성

git clone <저장소 URL> ~/uni-note
cd ~/uni-note/backend
git checkout <배포 브랜치>
SHA=$(git rev-parse --short HEAD)
docker build -t uninote-backend:$SHA .
```

이어서 로컬 데이터를 이전한다. 로컬 Backend를 중지한 뒤, 저장소 루트의 Windows PowerShell에서 덤프한다. PowerShell의 `>`는 인코딩을 바꿀 수 있으므로 `--result-file`을 사용하고, 실수로 커밋하지 않도록 저장소 밖에 저장한다.

```powershell
mysqldump -u <user> -p --single-transaction --no-tablespaces --set-gtid-purged=OFF `
  --default-character-set=utf8mb4 --result-file="$HOME\uninote.sql" uninote_db
```

DB가 참조하지만 `backend/uploads`에 없는 파일을 찾는다.

```powershell
Select-String -Path "$HOME\uninote.sql" -AllMatches `
  -Pattern '[0-9a-fA-F]{8}(-[0-9a-fA-F]{4}){3}-[0-9a-fA-F]{12}\.(png|jpe?g|gif|webp|pdf)' |
  ForEach-Object { $_.Matches.Value } | Sort-Object -Unique |
  Where-Object { -not (Test-Path "backend\uploads\$_") }
```

출력된 파일은 이전 후에도 표시되지 않는다. 원본을 찾아 `backend/uploads`에 넣거나, 해당 노트의 첨부를 다시 올린다. `application.yaml`의 `file-access.legacy-allowed-files`에 있는 파일 3개도 현재 로컬에 없으므로 함께 확인한다.

점검이 끝나면 덤프와 업로드 파일을 EC2로 보낸다.

```powershell
scp -i <key.pem> "$HOME\uninote.sql" ubuntu@<Elastic IP>:~/
scp -i <key.pem> -r backend\uploads ubuntu@<Elastic IP>:~/uploads
```

EC2에서 실행한다.

```bash
mysql --ssl-mode=REQUIRED --default-character-set=utf8mb4 \
  -h <RDS endpoint> -u <admin> -p uninote_db < ~/uninote.sql
sudo cp -r ~/uploads/. /opt/uninote/uploads/
rm ~/uninote.sql
rm -r ~/uploads
```

덤프에는 사용자 정보와 비밀번호 해시가 들어 있으므로 이전을 확인한 뒤 로컬의 `$HOME\uninote.sql`도 삭제한다. `FILE_SIGNING_SECRET`에 로컬의 `file.signing-secret` 값을 넣었는지 확인한다.

**완료 기준:** RDS에 테이블과 데이터가 존재하고, 업로드 파일이 `/opt/uninote/uploads`로 옮겨짐.

### 4단계: Backend 실행

4장의 `docker run`을 `validate` 설정 그대로 실행한다.

```bash
docker logs -f uninote-backend

curl -i -X POST http://127.0.0.1:8080/api/auth/login \
  -H 'Content-Type: application/json' -d '{}'
```

`validate`는 기동 시 DB에 연결해 스키마를 검사하므로, 기동 성공은 DB 연결과 스키마 일치를 뜻한다.

**완료 기준:** 로그에 `Started BackendApplication`이 있고, `curl`이 5xx가 아닌 4xx를 반환함. 기동에 실패하면 로그의 누락 환경변수나 스키마 오류를 먼저 해결한다.

### 5단계: DNS와 HTTPS

1. DuckDNS 웹에서 `uninote` 서브도메인의 current ip를 Elastic IP로 지정하고 저장한 뒤 전파를 확인한다 (`nslookup uninote.duckdns.org`).
   - Elastic IP는 바뀌지 않으므로 DuckDNS의 IP 자동 갱신 cron은 설정하지 않는다.
2. 7장 설정을 `/etc/nginx/sites-available/uninote`에 저장하고 적용한다.

```bash
sudo ln -s /etc/nginx/sites-available/uninote /etc/nginx/sites-enabled/uninote
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d uninote.duckdns.org --redirect
sudo certbot renew --dry-run
```
HTTPS 인증서 자동 갱신은 유지한다. `certbot` 패키지가 설치한 systemd timer가 갱신을 담당하며 `systemctl list-timers | grep certbot`으로 확인한다. DuckDNS IP 갱신과는 별개다.

3. CORS 응답을 확인한다.

```bash
curl -i -X OPTIONS https://uninote.duckdns.org/api/auth/login \
  -H 'Origin: https://<netlify-site>.netlify.app' \
  -H 'Access-Control-Request-Method: POST'
```

**완료 기준:** HTTP가 HTTPS로 전환되고, 응답에 `Access-Control-Allow-Origin: https://<netlify-site>.netlify.app`이 있으며, 인증서 갱신 테스트가 성공함.

### 6단계: Frontend 배포와 전체 점검

1. 8장대로 Netlify를 설정하고 배포한다.
2. 배포된 페이지 소스의 CSP(`connect-src`, `img-src`)에 `https://uninote.duckdns.org`이 있고 `localhost:8080`이 없는지 확인한다.
3. 11장 점검 항목을 전부 수행한다. `docker logs`와 `/var/log/nginx/error.log`를 함께 본다.

**완료 기준:** 11장 항목이 모두 통과함. 쓰기 동작이 실패하면 DB에 남은 사용하지 않는 `NOT NULL` 컬럼이 원인인지 확인한다.

### 7단계: 운영 체계 정리

- [ ] EBS 스냅샷 자동화 (AWS Data Lifecycle Manager, 일 1회)
- [ ] RDS 자동 백업 보존 기간 확인, 삭제 방지 활성화
- [ ] 스냅샷과 RDS 백업으로 복구를 한 번 시험
- [ ] 키 파일과 DB 덤프 등 임시 파일 삭제 확인
- [ ] 2GB 인스턴스에서 메모리 부족이 발생하면 `docker stats`로 확인 후 인스턴스 또는 JVM 힙 조정

### 재배포와 롤백

```bash
cd ~/uni-note && git pull
cd backend
SHA=$(git rev-parse --short HEAD)
docker build -t uninote-backend:$SHA .
docker stop uninote-backend && docker rm uninote-backend
# 4장의 docker run을 새 태그로 실행
```

- 엔티티가 바뀌었으면 변경 SQL을 RDS에 먼저 적용한다. 빠뜨리면 `validate`에서 기동에 실패한다.
- 문제가 생기면 컨테이너를 지우고 이전 SHA 태그로 다시 실행한다. DB 변경은 자동으로 되돌아가지 않으므로 호환되지 않는 스키마 변경 전에는 RDS 스냅샷을 남긴다.

### 후속 정리

상시 서버로 전환이 끝나면 `frontend/src/api/client.js`의 `ngrok-skip-browser-warning` 헤더를 제거한다. 남아 있어도 동작에는 문제가 없다.

현재 문서는 배포환경 설계 기준이며, 실제 AWS 리소스 정보·도메인·비밀값은 운영 환경에 맞춰 별도로 주입한다.
